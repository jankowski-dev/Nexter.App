## H1. Holdout считается без warmup

- **Статус:** подтверждена.
- **Доказательство:**
  - `ai-search.service.ts:659`: `runBacktest(definition, params, folds.holdout, {...})` — переданы только `initialCapitalUsd`, `feeBps`, `slippageBps`, `changeLookbackCandles`. **`warmupCandles` отсутствует** (сравни: `ai-search.evaluate.ts:45`, где для фолдов он есть).
  - `ai-search.helpers.ts:140`: `holdout: use.slice(searchEnd, total)` — только последние 30 дней = 720 свечей для 1h, без предшествующей истории. Для фолдов warmup = `max(15*perDay, 240) = 360` свечей (`helpers.ts:131-136`).
  - Аблация, стрессовый фикстурный прогон (300 вариантов, 10 прошли OOS-фильтры, текущий holdout: 0/10 положительных):
    - `momentum_breakout`: `now = 0.00% / 0 сделок` → `warm = +4.77% / 4 сделки`;
    - `squeeze_breakout`: `0.00% / 0` → `+1.51% / 2`;
    - `momentum_breakout`: `−0.94% / 2` → `+0.39% / 8`;
    - `squeeze_breakout`: `0.00% / 0` → `+0.11% / 4`;
    - `momentum_breakout`: `0.00% / 0` → `−0.28% / 4`;
    - всего **24 смены знака** по протестированным кандидатам (с учётом top-10/25/50/100).
  - Аблация без медвежьего хвоста: `momentum_breakout` 2.16%/8t → 6.94%/12t, `mean_reversion` 2.39%/6t → 5.84%/8t, `squeeze_breakout` 3.59%/8t → 5.10%/10t — warmup систематически увеличивает число сделок и доходность.
  - Оговорка: числа синтетические; на реальных свечах LINK/1h аблацию нужно повторить. Направление эффекта (отсутствие истории → 0 сделок или ложный минус) подтверждено.
- **Влияние:** напрямую объясняет расхождение «положительный OOS → отрицательный/нулевой holdout» и может объяснять часть из 0 рекомендаций. Искажает только holdout — финальный подтверждающий фильтр — поэтому эффект на итог максимален.
- **Severity:** Important.
- **Минимальное исправление:** в `buildSearchFolds` (`helpers.ts:138-141`) возвращать для holdout не только последние 30 дней, а префикс warmup (15 дней / 240 свечей) + сам holdout, и передавать `warmupCandles` в `runBacktest` на `ai-search.service.ts:659` так же, как в `evaluate.ts:45`. Тест: фикстура 1h с `slowPeriod=240`, проверить, что `runBacktest` получает `warmupCandles > 0` и что в holdout есть сделки; параметризованный тест для 1h/4h/1d.
- **Риск исправления:** изменятся абсолютные holdout-returns и список рекомендаций; нужна перебазировка метрик и артефактов. Нельзя компенсировать это ослаблением порогов.

## H2. Holdout проверяет только top-10 по OOS

- **Статус:** подтверждена как ограничение дизайна, **не подтверждена как причина 0 рекомендаций**; исправление повысит ложноположительные.
- **Доказательство:**
  - `ai-search.service.ts:653-654`: сортировка по `policyScore`, `metrics.slice(0, 10)`; holdout только для этих десяти (`:655-707`).
  - Аблация: в стрессовом прогоне OOS-фильтры прошли только 10 вариантов, поэтому top-25/50/100 дали те же 0/10 — вариантов №11–50 просто не существовало. Доказательства, что «№11–50 устойчиво положительные», нет.
  - Статистический аргумент (H10): holdout — подтверждающий тест, не участвует в отборе; top-10 уменьшает число сравнений с 5000 до 10. Расширение до top-50 при независимых тестах поднимает ожидаемое число ложноположительных с ~5 до ~25.
- **Влияние:** только чувствительность к попаданию в топ; само по себе 0 не объясняет.
- **Severity:** Minor.
- **Минимальное исправление:** не менять выборку. Добавить в `stats` счётчик «прошли OOS, но не попали в holdout-top-10» (`metrics.length - top.length`) — наблюдаемость без изменения политики.
- **Риск исправления:** переход на top-50 без множественной коррекции создаст рекомендации из шума.

## H3. Фильтры и их порядок

- **Статус:** подтверждена механика; причина 0 не доказана, данных для распределения нет.
- **Доказательство:**
  - Пороги: `ai-search.service.ts:81-84` — `MIN_TRADES=8`, `MAX_DRAWDOWN_PCT=20`, `MIN_POSITIVE_FOLDS=5`, `MIN_WORST_RETURN=-15`; плюс `oosMedian > 0` на `:586`.
  - Порядок: сделки (`:581`) → медиана OOS (`:586`) → фолды (`:590`) → DD (`:595`) → худший фолд (`:600`).
  - `trades` **суммирует все 8 фолдов**: `ai-search.helpers.ts:158` `results.reduce((sum, r) => sum + r.tradesCount, 0)`, данные из всех фолдов (`ai-search.evaluate.ts:38-47`). `tradesCount` учитывает обе ноги (`backtest.engine.ts:103,141`), каждый фолд принудительно закрывает позицию (`:271-276`). `MIN_TRADES=8` ⇒ требуется вход примерно в ≥4 из 8 фолдов.
  - 2894/5000 = 57.9% «мало сделок» совместно с 47.6% неположительной медианы OOS среди выживших согласуется с механическим несоответствием «широкий диапазон случайных параметров × короткие 10-дневные OOS-окна», но **не измерено**: артефакт поиска содержит только `stats/candidates/nearMisses/rejectionReasons` (план, раздел 6).
- **Влияние:** доминирующая причина отсева; может усугублять 0, но ошибкой не доказана.
- **Severity:** Minor (observability).
- **Минимальное исправление:** писать в `ai_artifacts.payload` per-variant dump (`strategyKey, params, trades, oosMedianReturnPct, positiveFolds, maxDrawdownPct, policyScore, holdoutReturnPct`) — только диагностика. Юнит-тест, что `aggregateVariant` суммирует сделки по всем фолдам. **Не трогать `MIN_TRADES`.**
- **Риск исправления:** рост размера артефактов; семантика метрик не меняется.

## H4. Stateful-стратегии и warmup

- **Статус:** подтверждена (холодное состояние), влияние в фикстуре умеренное.
- **Доказательство:**
  - `backtest.engine.ts:157-164`: warmup-свечи только добавляются в `samples`, **`definition.evaluate` на них не вызывается**; `strategyState = {}` (`:67`) и первый вызов `evaluate` — на первой OOS-свече (`:240-257`).
  - Зонд (H4b): на первой OOS-свече `ctx.state = {}`, `ctx.history.length = 361` для `trailing_stop`, `crash_protected_grid`, `failed_breakout` — состояние пустое несмотря на 360 warmup-свечей.
  - Аблация OOS с прогревом состояния (folds[3], 1h): `trailing_stop` 0.96%/2t DD 0.57 → 0.96%/2t DD 0.57 (без изм.); `crash_protected_grid` 1.12%/5t DD 1.85 → 1.21%/4t DD 1.54; `failed_breakout` 0/0 → 0/0.
- **Влияние:** реальный артефакт состояния; в текущей фикстуре эффект мал, но для стратегий, чей режим зависит от предшествующего OOS движения (high-water mark, режим обвала), может менять сделки и знак. Усиливает H1 на holdout.
- **Severity:** Important (архитектура), с оговоркой по измеренному размеру эффекта.
- **Минимальное исправление:** в `backtest.engine.ts` перед OOS-циклом прогонять `definition.evaluate` по warmup-свечам **без записи сделок** и инициализировать `strategyState` из последнего `nextState`. Тест: на первой OOS-свече `ctx.state` непустой для stateful-стратегий и число сделок в warmup = 0.
- **Риск исправления:** изменятся OOS-результаты stateful-стратегий; нужна перебазировка. Нельзя допускать запись сделок/эквити в период прогрева.

## H5. Look-ahead: решение и исполнение на одном close

- **Статус:** подтверждена как систематический оптимизм; **не объясняет** расхождение OOS+/holdout−.
- **Доказательство:**
  - `backtest.engine.ts:177-180` добавляет `closeUsd` в историю **до** решения; `:240-245` передаёт `priceUsd: candle.closeUsd`; `:262`/`:264` исполняют сделку по тому же `close`. Защитные выходы (`:186-237`) корректно используют open/high/low той же свечи.
  - Независимая аблация (26 свечей, конфигурация поиска): same-close **130.44%** / DD 9.40 / PF 10.92; next-open **120.78%** / DD 10.24 / PF 9.62 (−9.66 п.п.); next-close **62.12%** / DD 20.28 / PF 8.73 (−68.32 п.п., DD пересекает порог 20). Собственная аблация на OOS-фолдах дала меньшие измененения (например, `momentum_breakout` 2.01% → 1.93%; −0.08…+0.12 п.п.) — величина зависит от стратегии/фикстуры, направление одинаково.
- **Влияние:** завышает **и** OOS, **и** holdout; удаление look-ahead делает доходность ниже, поэтому не превращает отрицательный holdout в положительный и не объясняет near-miss. Снижает доверие к абсолютным уровням метрик.
- **Severity:** Important (систематическое смещение), не Critical для данного инцидента.
- **Минимальное исправление:** разделить цену сигнала и цену исполнения: решение по `candle.closeUsd`, исполнение по `open[i+1]` (или `close[i+1]`); блок `:186-237` не трогать. Тест-фикстура: отсутствие сделки по close свечи решения и цена исполнения = `open[i+1] * (1 ± slippage)`.
- **Риск исправления:** большой радиус — все бэктесты, 5000×8 фолдов, holdout, LAB/PDF, parity-тесты воркера и сопоставимость сохранённых артефактов. Нужна перебазировка; **не компенсировать порогами**.

Сортировка корректна (`ai-search.service.ts:953-955` + `.reverse()`; клиенты сортируют по возрастанию).

- **Влияние:** может сдвигать окна и искажать 24h-импульс; снижает доверие к метрикам. Contribution в 0 рекомендаций не измерено.
- **Severity:** Important (целостность данных), с оговоркой insufficient data.
- **Минимальное исправление:** добавить в `toCoverage` метрики expected-vs-actual и max gap в единицах таймфрейма, логировать mixed quality в `loadCandles`, строить границы фолдов по `openTime`, а не по индексу. Тест: 1h-фикстура на 4320 свечей с одной пропущенной и частью `quality='synthetic'`.
- **Риск исправления:** отбрасывание synthetic может сократить серию ниже 4320 и вызвать `Need at least 4320 candles` (`helpers.ts:120-122`). Сначала собрать статистику.

## H9. Агрегация и статистика

- **Статус:** подтверждена механика; найдены Minor-несоответствия имён/знаменателей.
- **Доказательство:**
  - Медиана для чётного числа фолдов корректна (`helpers.ts:144-151`): для 8 фолдов усредняются ранги 4 и 5.
  - `maxDrawdown = Math.max(...drawdowns)` (`:161`) — худший DD **одного** фолда с капиталом `$1000`, сброшенным каждый фолд (`ai-search.evaluate.ts:41`); это не DD единой капитальной кривой. Название `maxDrawdownPct` на уровне агрегата неоднозначно.
  - `policyScore = oosMedian − 0.5 * maxDrawdown` (`:162`): вариант может пройти все фильтры и иметь `policyScore < 0` (например, `+2` и DD 18 → `−7`), т.к. фильтры требуют только `oosMedian > 0` и `DD ≤ 20`. Сортировка идёт по `policyScore` (`:653`), поэтому это скрытый критерий отбора.
  - Знаменатели `stabilityPct` расходятся: helper делит на фактическое число фолдов (`helpers.ts:174`), сервис жёстко делит на 8 (`ai-search.service.ts:897-903`, знаменатель `:900`). Сейчас фолдов 8 — совпадает; при изменении числа фолдов — разойдётся.
  - `allMetrics` хранит **медианы OOS**, а не сырые доходности фолдов (`service.ts:576-580`), поэтому `bestReturnPct/averageReturnPct/medianReturnPct/worstReturnPct` (`:888-891`) идентичны `bestOosReturnPct/medianOosReturnPct/worstOosReturnPct` (`:894-896`) — их названия не отражают смысл. `holdoutReturnPct` (`:904`) — одно значение `recommended[0]`, при 0 рекомендаций `null`.
- **Влияние:** на выбор рекомендаций не влияет; влияет на интерпретацию статистики и устойчивость при смене числа фолдов.
- **Severity:** Minor.
- **Минимальное исправление:** переименовать/документировать дублирующие поля; выводить знаменатель `buildStats` из фактического числа фолдов; документировать, что aggregate DD = «худший DD фолда при сбросе капитала». Тест: совпадение `stabilityPct` helper/сервиса для 6/8/10 фолдов.
- **Риск исправления:** переименование ключей статистки может сломать фронтенд/читателей артефактов — нужны алиасы.

## H10. Верхнеуровневая политика «0 рекомендаций»

- **Статус:** подтверждена как статистически обоснованная; 0 — правдоподобный честный исход.
- **Доказательство/рассуждение:**

## Итоговый вердикт

### 1. Есть ли баг, объясняющий 0 рекомендаций?

**Частично.** Арифметики (H7) и генерации вариантов (H8) исправны; прямой подмеси дневных точек в 1h нет (H6); look-ahead (H5) смещает OOS и holdout в одну сторону и не объясняет расхождение. Но **H1 — реальная методологическая ошибка**: holdout запускается без warmup и без предшествующей истории, из-за чего стратегии с окнами/состоянием получают 0 сделок или ложный минус. На детерминированном стрессовом наборе это воспроизвело симптом «0/10 положительных holdout», а добавление 360-свечного префикса дало 24 смены знака и превратило несколько нулевых/отрицательных holdout в положительные. H4 (холодное состояние) усиливает эффект, H6 (gaps/mixed quality, не измерено на реальных данных) может дополнительно искажать окна. При этом наблюдаемые near-miss с сильным отрицательным holdout (−18.82%, −11.64%, −6.77%) указывают и на настоящий риск-режимный провал. **Вывод: до исправления H1/H4 и повторного прогона на реальных свечах результат «0» нельзя считать чисто рыночным.**

### 2. Какие 3 изменения дадут максимальный эффект без подгонки?

1. **H1:** добавить warmup-префикс к holdout в `buildSearchFolds` и передавать `warmupCandles` в `runBacktest` (`ai-search.service.ts:659`) — симметрично фолдам.
2. **H4:** прогревать состояние stateful-стратегий на warmup-свечах (вызов `evaluate` без записи сделок) до начала OOS/holdout.
3. **Наблюдаемость без изменения приоритетов:** per-variant metrics dump в `ai_artifacts`, счётчик «прошли OOS, но не вошли в top-10», корректные подписи отказов, метрики gaps/quality в coverage. Это делает H3/H6 измеримыми.

Отдельно, но не как способ получить рекомендации: H5 (исполнение на следующей свече) — систематическое завышение метрик; требует отдельной перебазировки. **Не делать:** top-50, снижение `MIN_TRADES`, ослабление DD/holdout — это manufacture ложноположительных.

### 3. Какие тесты/фикстуры добавить до следующего прогона?

1. Holdout-warmup parity: `runBacktest` получает `warmupCandles > 0`; `slowPeriod=240` на 1h даёт сделки в holdout; параметризовать 1h/4h/1d.
2. Stateful state-warm: первая OOS-свеча имеет непустой `ctx.state`; число сделок и точек эквити во время прогрева = 0.
3. Engine golden-фикстура из H7 (26 свечей): точные значения fee/slippage/amount/costBasis/PF/WR/DD/принудительного закрытия, сверенные с Python `Decimal`.
4. Data-quality фикстура: 1h, 4320 свечей, одна пропущенная + часть `synthetic`; coverage обязан показать не-`ok`/флаг, границы фолдов — по `openTime`.
5. Per-variant dump и stability-знаменатель: тест артефакта и совпадение `stabilityPct` для 6/8/10 фолдов.
