# Независимый аудит алгоритмов AI-поиска и бэктеста

Дата постановки: 2026-11-21. Статус: план для независимого ревьюера, production-код не менять.

## 1. Зачем этот аудит

Прогон LINK/1h на 5 000 вариантов дал **0 рекомендаций**:

- 2 894 варианта — «мало сделок»;
- 1 002 — неположительная медиана OOS;
- 489 — нестабильные фолды;
- 10 — слишком большая просадка;
- остальные — слишком глубокий худший фолд / отрицательный holdout;
- near-miss: `momentum_breakout` OOS +6,82% / holdout −18,82%, OOS +5,71% / holdout −11,64%, `squeeze_breakout` OOS +4,12% / holdout −6,77%.

Нужно ответить на три вопроса:

1. Это честный результат рынка/методологии или ошибка в коде?
2. Если ошибка — где именно и как её доказать на воспроизводимом наборе данных?
3. Какие минимальные изменения дадут объяснимое число рекомендаций без подгонки под историю?

## 2. Правила для ревьюера

- **Read-only**: не менять production, не запускать реальные сделки, не трогать секреты.
- Использовать существующие `ai_artifacts`/`ai_pipeline_runs` и локальные копии свечей; при необходимости — синтетические свечи с фиксированным seed.
- Любой вывод подтверждать файлом/строкой и числом (кол-во вариантов, сделок, доходность).
- Не «улучшать» пороги, чтобы получить рекомендации. Сначала диагноз, потом предложения.
- Отчёт — по шаблону из раздела 9.

## 4. Гипотезы, которые нужно проверить

### H1. Holdout считается без warmup (приоритет: высокий)

`ai-search.service.ts:654-665`: для top-10 вызывается `runBacktest(..., folds.holdout, ...)` **без** `warmupCandles`. `folds.holdout` — только последние 30 дней (`buildSearchFolds`), без предшествующей истории. Стратегии с `SMA/rollingHigh/ATR` на первых свечах holdout возвращают `null` или принимают решения без истории. Для 1h это 720 свечей (обычно хватает для SMA 20–60), для 4h — 180, для 1d — 30; для стратегий с окном 100–240 история может отсутствовать почти весь holdout.

**Проверить:** сравнить holdout для одних и тех же top-10 с текущим вызовом и с warmup-префиксом (15 дней/240 свечей до holdout) + `warmupCandles`. Замерить: число сделок, total return, сколько кандидатов меняют знак.

**Ожидание:** если без warmup много нулевых/отрицательных holdout при положительном OOS — это методологическая ошибка, а не рынок.

### H2. Holdout проверяет только top-10 по OOS (приоритет: высокий)

`ai-search.service.ts:654`: `metrics.slice(0, 10)`. Остальные положительные OOS-варианты holdout не проходят. Если top-10 случайно попали в плохой режим, рекомендаций будет 0, хотя варианты №11–50 могли быть положительными.

**Проверить:** прогнать holdout для top-25/50/100 по тому же OOS-score и посчитать, сколько из них положительные и проходят DD. Сравнить с текущими 10.

**Ожидание:** если среди №11–50 есть устойчиво положительные, текущая политика «top-10 only» — узкое место отбора, а не стратегии.

### H3. Фильтры и их порядок (приоритет: средний)

`MIN_TRADES=8`, `MIN_POSITIVE_FOLDS=5`, `MAX_DRAWDOWN_PCT=20`, `MIN_WORST_RETURN=-15`, `oosMedian > 0`; holdout — `return > 0 && drawdown <= 20`. Проверить:

- считает ли `trades` все 8 фолдов, а не только OOS;
- не отсекает ли `too few trades` варианты, которые в holdout торгуют;
- не является ли `MIN_TRADES=8` слишком высоким для стратегий с редкими входами;
- распределение `trades` и доходностей по стратегиям.

**Ожидание:** 2 894/5 000 «мало сделок» — подозрительно много. Нужна таблица «стратегия → медиана сделок → % отсева».

### H4. Stateful-стратегии и warmup (приоритет: высокий)

`runBacktest` заполняет `samples` warmup-свечами, но **не вызывает** `definition.evaluate` на них; `strategyState = {}` стартует только с первой OOS-свечи. Для `trailing_stop`, `crash_protected_grid`, `donchian_breakout` и других stateful-стратегий high-water mark/режим на начало OOS может быть неверным.

**Проверить:** для каждого stateful-варианта сравнить OOS с текущим поведением и с прогревом `evaluate` на warmup-свечах (без записи сделок), чтобы state был построен до OOS.

**Ожидание:** если state холодный, часть «нестабильных»/«мало сделок» — артефакт, а не стратегия.

### H5. Look-ahead: решение и исполнение на одном close (приоритет: средний)

`backtest.engine.ts:240-264`: `definition.evaluate` получает `candle.closeUsd`, затем buy/sell исполняется по тому же `close`. Это неисполнимо в реальности и может завышать OOS/holdout. Проверить, не является ли это причиной, по которой OOS положительный, а holdout отрицательный (если да — эффект скорее завышает оба, но направление надо измерить).

**Проверить:** исполнить решение на следующем open/close и сравнить OOS/holdout; отдельно — только на holdout.

### H6. Свечи: gaps, synthetic, duplicates (приоритет: средний)

Покрытие `4349 / 4320` не гарантирует непрерывность. Проверить:

- дубликаты/пропуски по `openTime`;
- `synthetic`/`quality` флаг;
- сортировку по времени;
- соответствие таймфрейму (1h);
- не подмешиваются ли дневные точки в 1h.

**Ожидание:** gaps могут сдвигать окна и ломать индикаторы; synthetic меняет stop/take fills (в движке это уже учитывается, но сравнить).

### H7. Издержки, размер позиции и P&L (приоритет: средний)

Проверить на ручном fixture:

- 25 bps fee + 10 bps slippage на buy и sell;
- `amount = usd / fillPrice`, `costBasis` включает fee;
- `totalReturnPct`, `maxDrawdownPct`, `profitFactor`, `winRate`, `tradesCount`;
- `initialCapital / maxAdds` и `reinvestProfit`;
- закрытие последней позиции в конце фолда;
- отсутствие двойного учёта fee/slippage.

**Ожидание:** сверить с независимым Python/pandas-расчётом на 20–50 свечах; расхождение > 0,01% — баг.

### H8. Генерация 5 000 вариантов (приоритет: средний)

`generateSearchVariants`: равномерное случайное поле, `JSON.stringify` для dedupe, defaults, отсев невалидных Zod. Проверить:

- сколько уникальных вариантов на стратегию;
- нет ли перекоса (одна стратегия получает 90% вариантов);
- не дублируются ли параметры после округления;
- не попадают ли в поиск стратегии с `aiEligible=false` (сейчас только `static_limit`).

### H9. Агрегация и статистика (приоритет: низкий/средний)

`aggregateVariant`: median/mean/worst по 8 фолдам, `positiveFolds`, `maxDrawdown = max`, `policyScore = median − 0.5*DD`, stability = positive/8. Проверить:

- median при чётном числе фолдов;
- `maxDrawdown` не берётся из одного фолда без учёта капитала;
- `policyScore` не сравнивает несопоставимые стратегии;
- `stats`/histogram не искажают total.

### H10. Верхнеуровневая политика «0 рекомендаций» (приоритет: высокий)

Даже при идеальном коде 0 — валидный исход. Нужно определить, является ли текущая политика (8 фолдов, 5/8 положительных, top-10, holdout > 0) статистически разумной для 5 000 вариантов и 30-дневного holdout. Проверить:

- ожидаемое число ложноположительных при 5 000 испытаниях;
- multiple-testing bias (выбор top-10 по OOS и проверка на том же holdout);
- не слишком ли короткий holdout (30 дней) для 8-фолдовой стратегии;
- сколько рекомендаций было бы при holdout 60/90 дней и top-50.

## 5. Воспроизводимые проверки

1. **Юнит-фикстуры движка:** ручной набор 20–50 свечей с известными buy/sell; посчитать P&L вручную; сравнить `runBacktest`.
2. **Независимый эталон:** тот же набор и параметры на Python/pandas; сравнить total return, max DD, trades.
3. **Holdout warmup ablation:** top-10 из последнего LINK-артефакта; прогнать holdout с warmup и без; таблица `strategy/params/OOS/holdout_now/holdout_warmup/trades`.
4. **Top-N ablation:** holdout для top-10/25/50; сколько положительных.
5. **Stateful warmup ablation:** прогнать `evaluate` на warmup-свечах и сравнить OOS.
6. **Next-open execution:** повторить OOS/holdout с исполнением на следующей свече.
7. **Data audit:** SQL/скрипт по `market_candles` для LINK/1h: gaps, duplicates, min/max, source, synthetic.
8. **Distribution report:** по каждому `strategyKey`: count, median trades, % too few trades, median OOS, % positive OOS, holdout pass rate.

## 6. Доступ к production-артефактам (read-only)

Не выводить секреты. Использовать `ai_artifacts` последнего поиска:

```sql
select r.id, r.started_at, r.finished_at, a.payload
from ai_pipeline_runs r
join ai_artifacts a on a.run_id = r.id and a.type = 'search'
where r.summary->>'variants' = '5000'
order by r.started_at desc
limit 1;
```

В `payload`: `stats`, `candidates` (recommended), `nearMisses`, `rejectionReasons`. Полных метрик всех 5 000 вариантов там нет — для аблаций нужно пересчитать на тех же свечах локально (скрипт/тест), не на production.

## 7. Что считать ошибкой

- **Critical:** сделки/доходность считаются неверно; look-ahead даёт систематическое завышение; holdout использует данные из OOS; state протекает между вариантами; fees/slippage не применяются.
- **Important:** holdout без warmup; top-10-only отсекает положительные варианты; фильтры несопоставимы со стратегиями; data gaps искажают окна.
- **Minor:** несогласованные названия метрик, отсутствие распределений, недостающие тесты.

## 8. Ограничения

- 5 000 вариантов × 8 фолдов — дорого; аблации можно делать на 200–500 вариантах и/или на top-50.
- 30-дневный holdout статистически шумный; выводы по одному прогону делать нельзя.
- Synthetic candles и DEX-данные могут быть неполными; это надо отделить от ошибок кода.
- Не менять пороги до подтверждения гипотез.

## 9. Шаблон отчёта ревьюера

Для каждой гипотезы H1–H10:

- **Статус:** подтверждена / опровергнута / недостаточно данных.
- **Доказательство:** файл:строка, команда/скрипт, числа до/после.
- **Влияние:** на 0 рекомендаций / на конкретные стратегии / на доверие к метрикам.
- **Severity:** Critical / Important / Minor.
- **Минимальное исправление:** что менять и какой тест это закрепит.
- **Риск исправления:** что может сломаться.

Итоговый вердикт:

1. Есть ли баг, объясняющий 0 рекомендаций?
2. Какие 3 изменения дадут максимальный эффект без подгонки?
3. Какие тесты/фикстуры добавить до следующего прогона?

## 10. Приоритет для ревьюера

Сначала H1 (holdout warmup), H2 (top-10), H4 (stateful warmup), H5 (next-open) — они наиболее вероятно объясняют расхождение «положительный OOS → отрицательный holdout». Затем H3/H6/H7, затем H8–H10.
