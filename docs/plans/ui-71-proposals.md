## 3. Предлагаемая структура раздела «Настройки»

Сейчас хаб смешивает изменяемые настройки, справочники, диагностику и импорт. Предлагаю:

```
/settings
├─ Учёт и отчёты          (timezone, gas, период статистики, экспорт)
├─ Рынок и графики        (M1–M5)
├─ Торговля и свопы       (T1–T9; T10 — после решения по allowlist)
├─ Роботы и бэктест       (B1–B9)
├─ ИИ и аудио             (I1–I4)
├─ Задачи и заметки       (N1–N5)
├─ Уведомления            (U2–U3)
├─ Интерфейс и поведение  (тема, автоблокировка, сеть, U1)
├─ Безопасность           (пароль, 2FA, сессии; вкладка «Аудит»)
├─ Диагностика            (объединить «Система» + «Качество данных»)
└─ Данные и экспорт       (счета, CSV/JSON, импорт Notion)
```

Что объединить/разделить:

- **Объединить** `Система` и `Качество данных` в `Диагностика` (обе read-only, один зритель, один интервал опроса).
- **Объединить** `Аудит` внутрь `Безопасность` как вкладку.
- **Разделить** текущую карточку `Общие`: редактируемые поля — в `Учёт и отчёты`, справочники — в `Данные`.
- **Вынести** из `ИИ` лимит аудио в подраздел «Вложения» (это не AI-настройка).
- **Добавить** `Рынок`, `Торговля`, `Роботы`, `Задачи и заметки`, `Уведомления`.
- **Оставить** в env и показывать read-only в `Диагностике`: execution flags, kill switch, allowlists, RPC, ключи, rate limits, TTL сессий, PBKDF2.

Рекомендуемый первый пакет (10–12 параметров): M1–M5, T1–T5, B2–B8, N1–N3, A3, U3.

## 4. Allowlist токенов: варианты

Сейчас swap-allowlist — это статический реестр в коде (`token-registry.ts`, 19 BSC + 6 ETH). Добавление токена требует правки кода и деплоя. Варианты:

### Вариант A. Группа «Основная» = allowlist (буквально)

Любой токен, добавленный в `Основную`, можно свапать.

- Плюс: ноль ручной работы.
- Минус: любой ошибочный/скам-контракт сразу становится доступен для исполнения; honeypot, fee-on-transfer, подмена адреса.
- Защита: разрешать только `asset.isVerified`, но тогда снова нужна ручная верификация.

### Вариант B. Группа «Основная» + отдельный флаг «Разрешить свопы»

Токен попадает в `Основную`, но по умолчанию `swapEnabled=false`; владелец включает тумблер в карточке токена. Это self-service, без правок кода.

- Плюс: контроль и аудит; нельзя случайно свапнуть скам.
- Минус: один клик на токен (но не запрос ко мне).
- Это мой рекомендованный вариант.

### Вариант C. Полностью автоматически, но с лимитами

Группа «Основная» = allowlist, но для новых токенов:

- лимит первой покупки (например, $50–$100);
- обязательный TOTP на первую покупку;
- проверка контракта (metadata, liquidity ≥ $25k, отсутствие honeypot-признаков);
- автоматический disable при аномалиях.
- Плюс: почти ноль трения.
- Минус: сложнее и всё равно не гарантирует безопасность.

### Вариант D. Оставить код, но добавить UI-кнопку «Добавить в swap-allowlist»

Кнопка пишет токен в БД/реестр, аудит, без деплоя. По сути B без группы.

**Рекомендация:** B. Реализация: поле `swap_enabled` в `watchlist` (или отдельная `swap_tokens`), async-проверка токена в swap-сервисе с кэшем, остальные router/executor/selector/wallet allowlists остаются в env. Никакие проверки calldata/approval/step-up не ослабляются.

## 5. Автоматическая покупка, стоп-лосс и тейк-профит

Главное ограничение: **на сервере нет и не должно быть приватных ключей**. WalletConnect/Tangem требует подтверждение владельца; полностью автоматическая подпись сейчас невозможна. Поэтому варианты:

### Режим 1. Dry-run / сигналы (безопасно, можно делать сейчас)

Правило считает условие и пишет событие/уведомление: «пора купить/закрыть», с ценой, причиной и ссылкой на предзаполненный drawer. Никаких записей в ledger/swap.

- Плюс: безопасно, проверяем поведение.
- Минус: владелец всё равно нажимает кнопку.

### Режим 2. Semi-auto (рекомендованный MVP)

Правило создаёт **предложение**: уведомление + deep link `/portfolio?action=close&groupId=...` (или buy), drawer открывается с готовым количеством/токеном; владелец подписывает.

- Для стоп-лосса/тейк-профита: считается avg cost и P&L, предложение закрыть 25/50/100%.
- Плюс: реальное исполнение, ключи не на сервере.
- Минус: нужен клик владельца; при быстром рынке можно опоздать.

### Режим 3. Ledger-only (не рекомендую)

Правило автоматически создаёт `transactions`/`lots` без реального свапа.

- Это только учётная запись, а не торговля; портит P&L и налоги, если реальная сделка не совершена. Допустимо только как «бумажный» журнал.

### Режим 4. Полный автомат (вне текущей архитектуры)

Нужен внешний подписант: session key / ERC-4337 smart account, keeper, limit-order protocol или CEX API. Это отдельный security review, хранение ключей/сессий, лимиты и мониторинг. Сейчас не делаем.

### Что добавить в UI

- В drawer создания/закрытия ордера — блок «Защита»: стоп-лосс %, тейк-профит %, trailing, частичные уровни. Сохраняется как правило для trade group.
- Новый раздел `Автоматизация` (8-я вкладка Crypto или подраздел `Роботов`): список правил, статус, условия, лимиты, журнал срабатываний, кнопка «Остановить всё».
- Настройки автоматизации: режим (dry-run/proposal), глобальный выключатель, max order USD, max daily USD, max actions/day, cooldown, минимальная ликвидность, разрешённые группы/токены.
- Все действия — в audit log и notifications.

### Модель правил (предложение)

- `buy_price` / `buy_drop_pct` / `strategy_signal`.
- `stop_loss_pct` / `take_profit_pct` / `trailing_stop_pct` для конкретной trade group.
- Частичные уровни: 50% на +5%, остаток на +10%.
- Оценка **по trade group**, а не по активу: у каждой группы свой cost basis и остаток.
- Idempotency: `ruleId + triggerKey`; advisory lock; никаких повторных срабатываний в один день без смены условия.

### Безопасность

- Глобальный `AUTOMATION_ENABLED=false` по умолчанию, kill switch.
- Лимиты на ордер/день/портфель, cooldown, max slippage/impact, max gas.
- Step-up TOTP для сумм выше порога; для proposal-режима — обычная подпись.
- Не использовать `sourceOverride` (он обходит policy-проверки).
- При stale/missing quote, closed group, mismatch asset, busy close order — пропуск с записью причины.

### Этапы

1. Read-only evaluator + dry-run + уведомления.
2. UI правил и журнал.
3. Proposal-режим (deep link, предзаполненный drawer).
4. Ledger-only — только если владелец явно подтвердит, что это ручной журнал.
5. Полный автомат — отдельный проект с подписантом/AA.
